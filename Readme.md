# E2E-тесты Labkeeper

Acceptance-тесты запускаются напрямую против настроенного `E2E_HOST`. В тестах нет моков, подмен ответов API и перехвата запросов.

## Требования

- Node.js 20 или новее.
- Docker для прогона в окружении, совпадающем с CI.
- Тестовый аккаунт, данные которого разрешено изменять.
- Captcha bypass token для входа и сценариев, начинающихся без сессии.

## Переменные окружения

Скопируйте `.env.example` в `.env` и заполните значения:

```dotenv
E2E_HOST=https://labkeeper.io
E2E_CAPTCHA_BYPASS_TOKEN=
E2E_USER_EMAIL=
E2E_USER_PASSWORD=
E2E_PROJECT_PREFIX=e2e-autotest
```

`E2E_SECOND_USER_EMAIL` и `E2E_SECOND_USER_PASSWORD` нужны только для сценария с публичным проектом другого авторизованного пользователя.

`ENABLE_LANDING_TESTS` включает сценарии, которые открывают лендинг. Лендинг отдается только production, поэтому переменная выставляется в ежедневном прогоне `scripts/k8s/cronJob.yaml` и не выставляется ни в долгой джобе репозитория редактора, ни на локальном стенде `scripts/local`. Значения `0`, `false`, `off` и `no` тоже выключают сценарии, чтобы не приходилось удалять строку из `.env`. Без переменной лендинговый сценарий остается в `npm run test:list` и попадает в отчет как skipped с причиной.

Без основной учетной записи можно запустить только безопасный набор `npm run test:anonymous`. Компиляционные сценарии используют временные авторизованные проекты, чтобы регулярный прогон не исчерпывал общий анонимный лимит production.

### Уведомления в ntfy

Если задана переменная `E2E_NTFY_URL`, вместо HTML-отчета итог прогона публикуется одним сообщением в топик [ntfy](https://ntfy.sh): статус, длительность, количество passed/failed/flaky/skipped и список упавших тестов с первой строкой ошибки. Учетные данные передаются через Basic-авторизацию. Так работает ежедневный прогон в Kubernetes.

```dotenv
E2E_NTFY_URL=https://ntfy.mipt.io/tests
E2E_NTFY_USERNAME=
E2E_NTFY_PASSWORD=
```

Репортер реализован в `tests/reporters/ntfy-reporter.ts` без сторонних зависимостей. Он находится внутри `tests`, потому что production-образ копирует только эту директорию поверх базового образа. Ошибка отправки уведомления пишется в stderr и не влияет на результат прогона.

Файл `.env` исключен из Git, а тесты не записывают значения email, пароля и bypass token в консоль. Локальные отчеты и артефакты также исключены из Git; учитывайте, что интерфейс приложения сам показывает email авторизованного пользователя на скриншотах.

## Локальный запуск

```bash
npm ci
npx playwright install chrome msedge firefox webkit
npm test
```

Полезные команды:

```bash
npm run check
npm run test:list
npm run test:anonymous
npm run test:authenticated
npm run test:chrome
npm run test:edge
npm run test:firefox
npm run test:safari
npm run test:android
npm run test:iphone
npm run test:performance
npm run test:scenarios
```

Для разработки можно использовать встроенный Chromium:

```bash
npx playwright install chromium
npm run test:local
```

По умолчанию полный прогон выполняется в профилях `Microsoft Edge`, `Google Chrome`, `Windows Firefox`, `macOS Safari`, `Android Chrome` и `iPhone Safari`. Профили Firefox и Safari используют движки Playwright Firefox и WebKit. Мобильные профили эмулируют Pixel 7 и iPhone 15. Все профили запускаются последовательно с одним worker, чтобы не создавать гонки за production-данные.

## Запуск в Docker

Локальный UI запускается из корня репозитория:

```bash
docker compose -f scripts/local/docker-compose.yml up --build
```

Playwright UI будет доступен на `http://localhost:9237`.

Обычный прогон внутри уже запущенного контейнера:

```bash
docker compose -f scripts/local/docker-compose.yml exec playwright npx playwright test
```

Для production укажите `E2E_HOST=https://labkeeper.io`. Для локального фронтенда используется nginx proxy, описанный в `scripts/local/nginx.conf.template`.

## Структура тестов

- `tests/specs` содержит только читаемые пользовательские сценарии.
- `tests/scenarios` содержит длинные сквозные бизнес-сценарии.
- `tests/performance` содержит проверки отзывчивости редактора.
- `tests/dsl/locators` содержит все DOM-локаторы и CSS-селекторы.
- `tests/dsl` содержит действия и проверки.
- `tests/fixtures.ts` создает DSL и выполняет очистку временных проектов.
- `tests/reporters` содержит ntfy-репортер для уведомлений о результате прогона.
- `docs/migration/playwright-tests.md` содержит матрицу переноса исходных тестов.

Проверка `npm run check:architecture` завершится ошибкой, если в spec-файле появится прямой локатор, если в тестах появится подмена сетевого запроса или если спека обращается к лендингу и не читает `landingTestsEnabled`.

## Производительность редактора

Набор `npm run test:performance` проверяет редактирование сегмента и файла на 1000 строк, работу со 100 сегментами и длительный повторный ввод в редакторах сегмента и файла. Большие данные подготавливаются до измеряемых действий только внутри временного проекта теста.

Для каждого измерения сохраняется JSON-вложение и выводится компактная JSON-строка в консоль. Отчет содержит задержки от ввода до обновления редактора и следующего кадра, промежутки между кадрами и доступные браузеру данные Long Tasks и Long Animation Frames. Основные проверки используют 95-й перцентиль, поэтому единичное колебание времени выполнения команды Playwright не определяет результат всего сценария. Максимальные задержки ввода и следующего кадра проверяются только по жесткому пределу зависания 2000 мс.

Для всех браузеров проверяется время от клавиатурного события до подтвержденного обновления редактора: p95 не должен превышать 100 мс. Чтобы p95 не совпадал с единственным самым медленным нажатием, в каждом сценарии набирается не меньше двадцати символов. Для WebKit-профилей p95 составляет 250 мс с учетом показателей однопроцессорного контейнера в Kubernetes. В Chromium и Firefox дополнительно проверяются задержка до следующего кадра с порогом p95 200 мс и промежутки между кадрами с порогом p95 100 мс.

Headless WebKit в однопроцессорном контейнере может приостанавливать `requestAnimationFrame` на непредсказуемое время, не задерживая обработку ввода и обновление редактора. Поэтому для macOS Safari и iPhone Safari кадровые показатели сохраняются в JSON как диагностические, а CI-ассерт использует стабильное время до обновления редактора. Максимальная допустимая задержка отдельного обновления остается общей для всех профилей.

Long Tasks и Long Animation Frames сохраняются в отчете полностью. Одиночный максимум не используется как самостоятельный CI-ассерт из-за подтвержденных выбросов планировщика однопроцессорного контейнера. Если браузер зарегистрировал не менее трех таких событий, их медиана не должна превышать 500 мс. Подготовка пробы и кадры ее стабилизации исключены из измеряемого интервала. Video и trace для performance-набора отключены, поскольку их запись искажает измерения.

Проект для проверки большого количества сегментов содержит 100 коротких Markdown-сегментов по одной строке. Время от завершения ответа API до готовности всех редакторов сохраняется как диагностическая метрика `responseToEditorReadyMs`. Оно не является CI-ассертом, поскольку включает инициализацию приложения, открытие мобильной панели и ожидание готовности DOM. Обязательный performance-ассерт этого сценария относится к прокрутке списка и редактированию последнего сегмента.

## Сценарий с примером LaTeX с лендинга

Сценарий `tests/scenarios/new-users/preview-latex-project-success-compile.spec.ts` проходит путь гостя: лендинг, «Примеры проектов», превью LaTeX-примера, гостевые запуски, вход постоянным тестовым аккаунтом, клонирование и компиляция своей копии. Без `ENABLE_LANDING_TESTS` вся группа пропускается.

- Пример берется из категории `diploma`. Остальные LaTeX-примеры подключают файлы проекта (картинки, `settings.sty`), а гостевая компиляция файлы не читает и заканчивается ошибкой.
- Гостевые запуски расходуют тот же дневной анонимный лимит адреса, что и анонимные проверки `access.spec.ts` во всех профилях. Поэтому они выполняются только в профиле `Google Chrome` и не больше трех раз. Если лимит уже исчерпан, сценарий проверяет окно входа и сообщение `Login is required to proceed`. Число успешных гостевых запусков и то, был ли достигнут лимит, пишутся в аннотации `guest compilations` и `anonymous limit`.
- Вход выполняется в той же модалке, которую гость получает по кнопке `Clone`, данными из `E2E_USER_EMAIL` и `E2E_USER_PASSWORD`. Без `E2E_CAPTCHA_BYPASS_TOKEN` сценарий пропускается: форма входа требует капчу так же, как регистрация.
- Лендинг отдается production, поэтому сценарий не запускается на локальном стенде из `scripts/local`: его nginx отдает на `/` локальный фронтенд.
- Клон попадает в список постоянного аккаунта, где название примера совпало бы сразу с несколькими строками. Поэтому сразу после клонирования сценарий переименовывает копию в уникальное имя с `E2E_PROJECT_PREFIX` и ищет в списке уже его.
- Политика конфиденциальности у постоянного аккаунта принята заранее, и окно не появляется. Если появится новая версия политики, сценарий ее примет, а сработавшая ветка пишется в аннотацию `privacy policy`.
- Регистрации с чтением реального письма в наборе больше нет: у production нет API удаления пользователя, и каждый прогон оставлял бы новый аккаунт. Потеря покрытия зарегистрирована условным сценарием `registration-with-real-email`.

## Проверка PDF

`ResultDsl` читает текст из слоя, который PDF.js создает после отображения PDF во фронтенде. Тест не скачивает исходный файл напрямую из S3. Доступны точное сравнение текста, проверка фрагмента, текстовый снапшот и визуальный снапшот страницы. Для визуального эталона берется PNG непосредственно из отрисованного canvas, поэтому в него не попадают кнопки и панели приложения.

Playwright хранит отдельные эталоны для каждого браузерного профиля. Намеренно обновить их после проверки результата можно командой:

```bash
npx playwright test tests/scenarios --update-snapshots
```

## Идемпотентность

Каждый изменяющий данные тест создает проект с уникальным именем, начинающимся с `E2E_PROJECT_PREFIX`. Созданные тестом данные регистрируются в fixture и удаляются в teardown, в том числе после падения основного сценария. При переименовании fixture хранит идентификатор проекта и оба возможных имени, поэтому cleanup удалит проект даже при задержке обновления интерфейса.

Очистка не удаляет проекты без зарезервированного префикса. Исключение составляет клон из лендингового сценария: он удаляется по идентификатору из ответа клонирования и от имени тестового аккаунта, независимо от названия. Название клона при этом сразу меняется на префиксное, чтобы упавший прогон было видно в списке проектов. Анонимные тесты получают новый BrowserContext и не используют состояние предыдущего теста.

## Условные сценарии

Сценарии, которые нельзя безопасно воспроизвести на production без дополнительных условий, зарегистрированы как `@conditional` и отображаются в отчете как skipped. Причина указана отдельно для каждого теста.

К ним относятся принудительные HTTP 425 и 500, исчерпание квоты, отключение OAuth-провайдера, специальный аккаунт `phystech.edu`, LLM-запросы, состояния HTTP 401, которые production не создает без подмены, и регистрация с реальным письмом: у production нет API удаления пользователя, поэтому каждый прогон оставлял бы новый аккаунт. Сценарий со вторым пользователем запускается автоматически, когда заполнены обе переменные `E2E_SECOND_USER_*`, иначе отображается как skipped.

Два сценария публичного проекта реализованы полностью, но динамически пропускаются, если production ограничивает анонимную компиляцию ответом HTTP 425. Исходный `compilation-401-test` зарегистрирован как условный: после удаления сессии production возвращает HTTP 200 при доступной анонимной квоте и HTTP 425 после ее исчерпания, но не HTTP 401.
